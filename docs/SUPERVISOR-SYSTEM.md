# Supervisor system — Stage 13

**Status: STAGE 13 — PARTIALLY COMPLETE.** Every module below is implemented,
verified in a real browser and (where a backend is involved) against the
real backend from Stage 12.2. What is not connected: a deployed backend,
real supervisor accounts, and the business decisions the architecture
deliberately leaves open (§9). The five launch supervisors remain
placeholders until the business supplies their names, photos and contact
channels — unchanged from Stage 10.

*(The five launch supervisors below were subsequently populated with DEMO
/ PLACEHOLDER data — real names still to come from the business — and a
real attribution bug this stage's architecture had was found and fixed;
see `docs/SUPERVISOR-PROFILES.md`. This file's own historical claims are
left as written above.)*

## 1. What this stage adds

Travel & Tourism already had (Stage 10) a public supervisor profile and (Stage
10.9) attribution stored with a booking. Stage 13 makes the supervisor a
**first-class, authenticated party** in the system:

- a supervisor account, session and portal — separate from the customer
  account, on the same backend (Stage 12.2's `backend/`);
- server-authoritative attribution with an audit trail;
- customer, lead, booking, revenue and performance views scoped to that one
  supervisor, enforced in SQL, never by the frontend;
- a scalable data model (`supervisors` table, arbitrary count) instead of
  five hard-coded UI branches;
- an architecture prepared for the future Admin Dashboard (Stage 14) —
  reassignment and profile management functions exist and are tested, but
  no admin UI is built.

Nothing about the existing public profile, the booking engine or the
customer account changed in appearance or behaviour; the profile page
(`assets/js/components/supervisor.js`, `assets/js/data/supervisors.js`) is
untouched.

## 2. Supervisor data model

`assets/js/data/supervisors.js` (Stage 10) remains the source for the
**public profile**: `id`, `slug`, `status`, name/title/bio (Ar/En), image,
languages, specialties, services, phone/whatsapp/email, `createdAt`. It is
explicitly a registry a future admin will edit; Stage 13 does not replace
it, per the brief's "do not redesign".

The backend's `supervisors` table (`backend/migrations/002_supervisors.sql`)
is a **superset** prepared for that future admin: the same public fields,
plus `internalId`, credentials (`password_salt/hash`, never exposed),
`notification_prefs_json`, `created_at/updated_at`. It is what
`/supervisor/me` (§25) reads and writes, and what a real backend's public
directory would eventually serve if the profile page is ever switched to
read live data — a decision left to the business/Stage 14, not made here.

**Scale.** Every query in `backend/supervisor.mjs` is parameterised by
`supervisor_id`, never by count: adding a 6th, 50th or 500th supervisor is
one row (`supervisors`), not a code change. `SUPERVISOR_REGISTRY`'s array
literal is the one place the launch count of five is still explicit
(Stage 10), and it is a plain array — appending a record is enough.

## 3. Public profile — unchanged, and its unique URL

Route: `supervisor/<slug>/`, generated by `tools/build-routes.mjs` from
`SUPERVISOR_REGISTRY`. Slugs must be unique (`SUPERVISOR_REGISTRY` array),
URL-safe, and never one of the portal's own routes — see **reserved slugs**
below. An inactive supervisor's profile shows the "currently unavailable"
state (Stage 10) with a way back to booking or contact; the CTA does not
attribute a customer to an inactive supervisor (`isActiveSupervisor` gates
`saveAttribution`, `backend/supervisor.mjs`'s `assignAttribution` rejects
an inactive or unknown id).

### Reserved slugs

`assets/js/data/supervisors.js` exports `RESERVED_SUPERVISOR_SLUGS`
(`dashboard`, `customers`, `leads`, `bookings`, `revenue`, `performance`,
`notifications`, `settings`, `profile`, `sign-in`, `sign-up`, `sign-out`,
`forgot-password`, `reset-password`, `admin`, `me`, `auth`, `api`) and
`isValidSupervisorSlug()`; `backend/supervisor.mjs` carries the same list
server-side. These are exactly the supervisor portal's own private pages
(§11), which live at `supervisor/<reserved>/` beside the public profiles at
`supervisor/<real-slug>/` — a real slug can never collide with them.
`tools/build-routes.mjs` skips these directories when it cleans up
retired public-profile folders, so the hand-authored portal pages are
never deleted by the content tool.

## 4. Attribution — the model, and what is still open

Referral: `?supervisor=<slug>` on any door → `saveAttribution()`
(`core/booking.js`) stores it in `sessionStorage` for an **active**
supervisor only. It survives navigation, service selection, sign-up/sign-in
(carried as `supervisorId` on `signUp`), booking, payment and confirmation
(`assets/js/booking/journey.js`'s `attributionOf()`), because it travels
inside the booking context the whole way, and lands in the backend at
`POST /me/bookings/claim`.

**The business rule.** `backend/supervisor.mjs`'s `attributionModel()`
reads a `business_config` row seeded by the migration:

```json
{ "rule": "first", "status": "pending_business_confirmation" }
```

**FIRST ATTRIBUTION** is what the system already does (Stage 10.9 onward:
`assignAttribution()` never overwrites an existing `attribution_supervisor`)
and is preserved here, not invented — it is the one rule that matches "do
not silently reassign, do not overwrite unexpectedly" without the business
having chosen. LAST ATTRIBUTION, MANUAL ASSIGNMENT and HYBRID are not
implemented; changing the stored `rule` value is what a future admin
surface would do, and `assignAttribution()` is the one function that would
need a branch added for it.

**Audit trail.** Every attribution touch — at sign-up, at booking claim
(including a no-op when one already existed), and any future reassignment
— is written to `attribution_events` (`customer_id, supervisor_id,
previous_supervisor_id, source, actor, at`), append-only, server-controlled.
A customer's `attributionHistory` (visible to their supervisor, §14) is
read straight from this table.

## 5. Roles and authorization

Three roles exist in this backend: **customer**, **supervisor**, and a
placeholder for **admin** (Stage 14, not built). There is no role field
anywhere the browser can set: a customer is whoever `no_session` resolves
to, a supervisor is whoever `no_supervisor_session` resolves to — **two
separate cookies, two separate database tables, two separate session
tables** (`sessions` vs. `supervisor_sessions`). A browser holding both
cookies (e.g. QA) still cannot use one to satisfy the other's routes: `/me/*`
never reads `no_supervisor_session` and `/supervisor/me/*` never reads
`no_session` (`backend/server.mjs`). There is no "role" string transmitted
or trusted anywhere.

CSRF: the same double-submit design as the customer session, on the
session's own token (`X-CSRF-Token` compared against whichever session —
customer or supervisor — is live for that request). Verified: missing,
invalid, valid, and an expired/revoked session's token, plus a forged
cross-origin request (rejected by CORS before it reaches the check) —
`tests/backend.mjs`.

## 6. Customer/supervisor boundary

Every read in `backend/supervisor.mjs` filters by the session's
`supervisor_id` in the `WHERE` clause — `supervisorCustomers`,
`supervisorCustomer`, `supervisorBookings`, `supervisorBooking`,
`supervisorLeads`, `supervisorRevenue`, `supervisorPerformance`,
`supervisorCommissions`. A foreign id (customer, booking or lead belonging
to another supervisor) is a **404**, identical in shape to an unknown id —
existence is never confirmed. Verified with two supervisor fixtures
(`tests/backend.mjs`, `tests/supervisor-portal.mjs`): URL id substitution,
direct API calls, and — in the browser suite — the full flow (a real
customer, attributed through the public profile and a real booking,
visible to the correct supervisor and invisible to the other one).

## 7. Supervisor dashboard — modules

All under `assets/js/supervisor/` (domain: `auth.js`, `data.js`; adapters:
`dev-*`, `api-*`, `not-connected`, `installed.js`; screens: `ui/*.js`), the
same layered architecture as the customer account (Stage 12). Routes (all
private, guarded — §8):

| Route | Screen |
| --- | --- |
| `supervisor/sign-in/` | Sign in (no sign-up: accounts are provisioned by the business) |
| `supervisor/forgot-password/`, `reset-password/` | Password recovery |
| `supervisor/dashboard/` | Overview: performance metrics, revenue summary, recent leads, notifications |
| `supervisor/customers/` (+`?id=`) | My customers: search, list, detail with bookings and attribution history |
| `supervisor/leads/` | Leads: list, status change (new → contacted → in_progress → converted/closed) |
| `supervisor/bookings/` (+`?id=`) | Bookings: filter by status, list, detail |
| `supervisor/revenue/` | Gross / completed / pending / cancelled, period filter, commission status |
| `supervisor/performance/` | Customers, leads, conversion rate, bookings, period filter |
| `supervisor/notifications/` | A separate feed from the customer's, quiet refresh on focus |
| `supervisor/settings/` | Bio, phone, WhatsApp, city, password — nothing else |
| `supervisor/sign-out/` | Sign out |

No admin, no operations dashboard, no commission payout screen — out of
scope per the brief and not built.

## 8. Route security

`assets/js/supervisor/ui/shell.js`'s `mountSupervisorPortal()` calls
`restoreSupervisorSession()` before painting anything; a non-`supervisor`
status renders the guard state (sign-in prompt or "session expired") and
never reaches the screen's data calls. Every backend `/supervisor/me/*`
route independently requires a live `supervisor_sessions` row — the
frontend guard is UX, the backend check is authorization (§5/§6). Verified:
every portal route blocked for a guest, a customer session on a supervisor
route (401), a supervisor session on a customer route (401).

## 9. Commission / supervisor rights — architecture, not a rule

`commissions` table: `id, supervisor_id, booking_id, amount, currency,
status, period, rule_version, created_at`. `business_config`'s
`commission_model` row starts `{ "model": null, "status":
"pending_business_configuration" }`. `GET /supervisor/me/commissions`
always answers with that model alongside whatever rows exist (none today);
the revenue screen shows the same honest sentence rather than a number.
**No percentage, fixed amount, service-specific or hybrid rule is
calculated anywhere** — implementing one is a data change (`business_config`
+ a job that inserts `commissions` rows when a booking is billable), not an
architecture change. A supervisor cannot edit their own commission: it is
not a field `PATCH /supervisor/me` accepts.

## 10. Reassignment and audit trail

`reassignAttribution(customerId, newSupervisorId, actor)`
(`backend/supervisor.mjs`) moves a customer's **current** attribution
pointer, logs the change (`previousSupervisorId` kept) and leaves every
past booking's own `supervisor_id` untouched — a supervisor who closed a
sale keeps the historical record of it even after a reassignment. It is
reachable today only through `POST /admin/attribution/reassign`, gated by
a bearer token (`BACKEND_ADMIN_TOKEN`) that is **unset by default** — the
route answers 404 until an operator configures it, and even then requires
the exact token (403 otherwise). This is the one entry point Stage 13
prepares for Stage 14's Admin Dashboard (§40 of the brief); no admin UI
exists, and a supervisor's own session can never call it (it is not under
`/supervisor/me/*`). Verified in `tests/backend.mjs`: no token configured
→ 404 story is exercised with the token *unset* in a dedicated config
check; with a token configured (the default in the test suite's own
backend), wrong/missing tokens → 403, the correct token reassigns and the
history is preserved.

## 11. Customer account integration

Unchanged from Stage 12: a customer's account (`account/`) shows their
assigned supervisor's name and a link to the public profile
(`assets/js/account/ui/shell.js`'s `supportEntry()`), and the request-help
door. It never shows commission, internal performance, or any other
supervisor-private data — there is no such field on the customer-facing
`publicCustomer()` shape.

## 13. Responsive, RTL/LTR, accessibility

The portal reuses the account shell's grid (`.c-account`, `.c-acct-nav`),
verified at 390/834/1440 in Stage 12; Stage 13 adds its own layer
(`assets/css/23-supervisor-portal.css`) for metrics, the responsive table
(a real `<table>` at ≥48em, stacked cards below it — no required horizontal
scroll), filters and lead cards, all logical-property based. Verified in
`tests/supervisor-portal.mjs` at 390/834/1440 × Arabic/English: one `<h1>`,
no horizontal scroll, ≤1 dominant CTA, no sub-12px text, every control
labelled, the nav's current item marked, full English on the English
build. A table row's link (`.c-svp-link`) is a plain link, not the card
grid's `.c-card__link` stretched-overlay pattern, which does not confine
itself to a table cell.
