The design constraint

There is no server here, so there is no event stream to read. A log can therefore only be reconstructed from the current state of the other modules' data. That reconstruction is the whole design of this stage, and its limits are printed on the page rather than papered over.

03

Two refusals

Both are visible on the page rather than buried in a comment, because an operator reading an audit record needs to know which parts of it the system actually witnessed.

Unknown actor

غير مسجّل

The services, media and settings modules record what changed but not who changed it. Filling that in with a plausible administrator would put a false attribution into an audit record — worse than an honest gap, and undetectable once written. 25 of the 74 rows say so.

Unknown time

التاريخ فقط

Where a source stores a date and no time, the cell says so rather than showing 00:00. Those rows sort at the end of their day, so an undated change never jumps ahead of a timed one that preceded it.

A third, smaller one: النظام and نموذج الموقع are recorded actors but not people, so they get a neutral marker instead of initials in the actor column. The filter is labelled المنفِّذ — the performer — not المستخدم, because two of its values are not users.

04

Notification rules

Three rules, each tied to something an operator has to do about it. No notification exists that does not point at a real record, and none is generated for its own sake.

R1 A request still sitting in جديد — not yet triaged. Links straight to the request. 5 notifications
R2 A request left in قيد المراجعة for more than a day — stalled. One notification naming both request ids, and it never auto-reads. 1 notification
R3 A request that reached مؤكد, مكتمل or ملغي within 72 hours — news the team may not have seen. 3 notifications

Unread is never signalled by colour alone, per WCAG 1.4.1: an unread row carries bold weight, a dot, and the word غير مقروء. The row is a link with its own separate mark-read button beside it — never a control nested inside a control.

05

Read state

Seeded by age — anything older than 48 hours is assumed already seen — then overridden by whatever this browser has stored, under a single key shared by every page. Marking a notification read in the header popover marks it read on the module page, and the count in the header, the sidebar badge and the tab all move together because they read the same number.

What this is not

localStorage is per-browser, not per-account. Two administrators on the same machine share a read state; one administrator on two machines has two. On a real system this belongs to the signed-in account, on the server. It is the nearest a static build gets to an inbox, and it is labelled as such in the demo banner at the top of the module.

06

Shell changes

Adding a module means touching every page, so both changes were made once and applied uniformly rather than page by page.

  • Nav item — الإشعارات والنشاط joins the النظام group in both the sidebar and the mobile drawer, carrying the unread count as a badge.
  • Header bell — the popover was three different shapes across the eight existing pages: one with a mark-all button and a footer link, one with four hard-coded items, six with a single item and no footer. It is now one shape everywhere, showing the same five newest notifications the module derives, with a footer link to the full list.

The الرئيسية activity card now shows the four newest real events and links to the full log, which is also how the first of the defects below came to light.

07

Defects fixed

All four are in pages earlier stages had already signed off. Building a view over the other modules is what exposed them: a claim on one page is checkable once another page derives the same fact.

S14-01

The dashboard's activity card contradicted the real modules

Claimed
إخفاء خدمة «التنقل للمناسبات الاجتماعية» مؤقتاً — a hidden service, while services.html has all seven published (on:true). And تحديث محتوى «من نحن» — an edit in a المحتوى module that does not exist.
Impact

Fix
Replaced with the four newest events the log derives, plus a link to the full log.
S14-02

20 dead links on the dashboard

Found
Five KPI cards, five distribution legend rows, two “view all” buttons, the five newest requests in both table and card form, and three quick actions — all href="#". Stage 16's sweep only covered nav links.
Fix
All now resolve, which needed one small addition: requests.html?status=review pre-selects the status filter, so a KPI card lands on the list it counts instead of an unfiltered page. تعديل محتوى الموقع is marked pending like the nav item, because that module is not built — a disabled control is honest, a dead link is not.
S14-03

initials() returned the definite article

Found
نورة العتيبي rendered as ن ا — the alef of ال — where the shell's own hard-coded avatar reads ن ع. Latent in customers.html and users.html; visible the moment the log rendered an actor column.
Fix
Strip a leading ال before taking the letter. Applied to all three pages together so they cannot drift apart again.
S14-04

Arabic number agreement

Found
2 طلبات — plural where Arabic takes the dual. And قبل 2 ساعتين, where the dual already carries the count.
Fix
A plural() helper covering all four cases: 1 singular, 2 dual, 3–10 plural, 11+ singular accusative. The stale alert now reads طلبان, and relative times read قبل ساعتين.

09

What this still isn't

Stage 16's verdict does not move. Two of the four absent modules now exist — المحتوى and التقارير still do not — and that is the only line of the audit this stage changes.

  • A log the server writes. This one is reconstructed from current state, so it can only show changes the modules happen to record. Deletions leave nothing behind. Failed sign-ins, permission changes and settings edits are never written down, so they cannot be read back.
  • An audit trail. An audit trail is append-only at the storage layer. This one is read-only in the interface, which is a different and much weaker guarantee — anyone who can change the underlying data changes the log with it.
  • A notification system. Nothing is delivered anywhere. The settings page already says the system sends no email or SMS, and that remains true.

What the backend has to provide

  1. An events table written on every mutation — actor, module, action, target, timestamp — so the two refusals above stop being necessary.
  2. Per-account read state, replacing the shared localStorage key.
  3. Server-side authorization on the log itself. An activity record that a مدير المحتوى can read in full is an information leak, and no frontend check prevents it.
