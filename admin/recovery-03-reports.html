The specification, found

§03 says to inspect the approved specification before implementing anything, and §29 says the existence of source data is not approval. Both only mean something if the specification can actually be found. It can: admin/stage-02-admin-ux.html, module 08.

Every sentence there is a requirement, and several are unusually specific — "read the answer in words", "a wider one instead of a row of zeroes", "comes back to the same report and period". Those are the parts of the build that would have looked arbitrary without the source, so they are worth pointing at: the page opens with a sentence, not a grid of tiles; an empty period names the nearest period that has data and offers a button to it; and the report and period live in the address so the browser's own Back button honours the exit rule.

02

What is deliberately absent

The brief spends more words on what not to build than on what to build, and it is right to. Four things a reporting module reaches for by reflex are missing here, each because a clause says so.

Not builtClauseWhy
Export§18 Permitted only if explicitly approved. The specification names none, so /api/admin/reports/export is a 404 and the suite asserts it.
Charts§16 Permitted only where part of the approved specification. It names none. The share bars beside each count are a second reading of a number that is always printed — the dashboard's own existing treatment — and are aria-hidden, so nothing is communicated by colour alone.
Rates & averages§29 Completion rate, cancellation rate, average response time, retention, growth, forecasts. All listed by name in the brief. All computable from this data. None approved.
A reporting table§02 Every figure is a COUNT over the live operational rows. The suite asserts no table exists whose name contains report, metric, analytic, aggregate or snapshot.

The rule that did the most work

§29: the existence of source data does not mean a metric is approved. Every request carries a status and a timestamp, so a completion rate is one division away and a month-over-month trend is one GROUP BY away. Neither appears in the specification. The temptation to add them is precisely what the clause exists to stop, and the honest reading is that a reporting module which answers two questions well is worth more than one which answers twelve questions nobody asked.

03

The two reports

"Request and customer counts" names two, so there are two. A third returns 404 rather than an empty page — the endpoint knows the approved set, and does not serve outside it.

  • طلبات النقل خلال الفترة — the total, then the breakdown by each of the five approved statuses (always all five, a zero being a fact rather than a gap), by service, and by source.
  • العملاء خلال الفترة — how many distinct customers had a request, how many of them were new, how many returning, and the all-time registered total for context. New plus returning equals active by construction, which the suite asserts.

The answer appears first, as a sentence: «خلال آخر 30 يوماً، سُجِّل 12 طلباً.» Then the figures, then the breakdown. That order is the specification's, not a layout preference.

04

Which date is "a period"?

A request carries two dates: created_at, when it was logged, and trip_date, when the trip is. The specification says only "a period". Those two give different answers — a trip booked in August for September belongs to different months depending on which you count.

§12 — "do not apply undocumented assumptions"

Picking one silently is exactly that. So the basis is a labelled control — تاريخ تسجيل الطلب or تاريخ الرحلة — and every answer line names which one it counted. A figure that does not say what it measured is not a figure; it is a number.

Ranges are validated rather than repaired. An end before a start is an error, not something to quietly swap — the operator asked for something that does not exist and should be told. A same-day range is valid. A span beyond ten years is refused. An impossible calendar date is refused. All six of those cases have a test.

05

Read-only, structurally

§25 says a report must never modify operational data. That is easy to intend and easy to break later, so it is enforced in three independent places.

The repository

Every statement is checked before it runs

Repo_Reports contains no INSERT, UPDATE or DELETE, and every query passes assertReadOnly() first. A future edit that added one would throw, not succeed.

The route table

There is no POST to a report

One GET /api/admin/reports, gated on the existing reports permission. No write verb reaches this module at all.

The activity log

Reading a report writes nothing

§27 forbids activity noise from views, filters and sorts. Sixteen report runs are asserted to leave the request, customer, service, status and activity-log counts exactly where they were.

06

Drilling out and back

"Open any figure as a filtered request list" is a real link, not a phrase. Every non-zero figure and every breakdown row opens طلبات النقل carrying the period as from/to, the basis as dateby, and its own status or service.

Report → records → report figure→ requests.html?from&to&status→ the records behind it ↩ Back→ same report, same period

requests.html gained that range filter in this stage. It is what makes §12's accuracy requirement checkable by clicking rather than by reading code: the report says 9 in جديد, the list it opens says «عرض 1–5 من 9 طلبات» with the period and status shown as removable chips. Both numbers were read out of a live browser and compared.

The report and period live in the address, so the browser's own Back button returns to both. That is P10 — and it is why the exit rule in the specification is satisfied by the platform rather than by a bespoke history stack.

07

Data minimisation

§09 and §20 ask for the minimum the approved report requires. A count report needs a name to be readable and a number to be a count. It does not need a way to contact anyone.

So the customer report row is id, name, count, lastAt — and the suite proves it three ways: it greps the response for a Saudi mobile pattern, for @aunaldrb.com, and for a known trip origin, then asserts the row's key set is exactly those four. A phone number added to that response later would fail the build.
