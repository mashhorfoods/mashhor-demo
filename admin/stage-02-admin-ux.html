01

What the site actually is

Stage 02 was read against the built site before any flow was drawn. Four facts came back that change the UX, and they are stated first because every later section depends on them.

F1

There is no request form on the website

Shapes the whole module
Evidence
The تواصل معنا section contains zero <input> and no <form>. The only contact affordances on the entire page are tel:+966535544352 and wa.me/966535544352.
Consequence
طلبات النقل is not an inbox. Requests arrive by phone and WhatsApp, and someone types them in. So recording a request is a primary action, not a rare one — it belongs on the dashboard, on the requests list, and inside the customer profile.
Design for
The record form is used while the admin is on the call. That is the single most demanding flow in the product: fast, forgiving, phone-shaped, and it must never lose typed input.
Future
One field — مصدر الطلب (phone / WhatsApp) — keeps the module ready for a website form later without restructuring. See D1.
F2

FAQs and testimonials have nowhere to appear

Needs a client decision
Evidence
Neither الأسئلة الشائعة nor آراء العملاء exists anywhere in the built page.
Consequence
The dashboard can manage both, but saving one publishes it nowhere. Managing content that has no destination is the fastest way to lose a client's trust in a CMS.
Resolution
Both content types ship, and both carry a standing, honest status: لا تظهر على الموقع بعد — shown on the content hub and inside each editor, until a website section exists to receive them. See D2.
F3

Contact information has two candidate homes

Evidence
Stage 01 lists معلومات التواصل under both المحتوى and الإعدادات, while also forbidding duplicated content management.
Resolution
Contact information is company data, edited once, in الإعدادات — it feeds the header, the contact section and the footer simultaneously, so it is not a page of copy. المحتوى shows it read-only with a link, never a second editor. One field, one home.
Also
The site currently carries no social links at all. That settings category ships empty rather than inventing accounts.
F4

The site has three editable areas Stage 01 did not list

Evidence
Live sections include كيف نعمل (3 stages), رؤيتنا ورسالتنا, and القيم (6 values) — all real published copy.
Consequence
Stage 01's content list was introduced with "such as", and the built site is the source of truth. All three enter المحتوى. Leaving them out would mean the client can edit two-thirds of their own page.
Not added
Nothing else. No blog, no media library, no pages builder.

03

Operating rules

The Stage 01 principles restated as rules that can be checked against a screen. Each is testable.

RuleStatementHow it is checked
R1One screen, one question. Every screen answers a single question the client actually asks.Name the question. If it takes an "and", the screen is doing two jobs.
R2Two moves to any record. Any request or customer is reachable in at most two interactions from الرئيسية.Count the taps from a cold start.
R3Never lose the place. Finishing an action returns the user to where they started it, in the state they left it.See the context contract.
R4Never lose the typing. No error, validation failure, or accidental navigation discards entered text.Fail a save on a full form; the values survive.
R5One modal deep. Confirmations and filter sheets never stack on each other.No path opens a second overlay above the first.
R6Status is never colour alone. Every state carries a word; colour only reinforces it.Greyscale the screen — meaning survives.
R7Reversible beats destructive. Where hiding achieves the goal, deletion is not offered.Count delete actions in the product. Each one must justify itself.
R8RTL is the layout, not a switch. Reading, navigation, progression and table columns all run right to left.Nothing mirrors incorrectly; numerals and phone numbers stay Western and LTR.
R9Same verb, same behaviour. Save, cancel, filter and status change behave identically in all eight modules.The pattern matrix has no exceptions column.
R10Plain Arabic, no system words. The interface names things the way the client says them out loud.No "record", "entity", "slug", "publish state", "CMS", "API".

What RTL actually means here

Primary navigation sits on the right. Progression moves right to left, so the return control sits at the start of the content — the right edge — and its arrow points right (→), toward where the user came from. Table columns read right to left, with the identifying column first on the right. Phone numbers, dates, times and counts stay in Western digits and keep their own left-to-right run inside the Arabic line.

04

The global flow

One spine, followed by every module without exception.

Global task spine تسجيل الدخول→ الرئيسية→ Module→ List→ Filter / search→ Record→ Action→ Confirm→ Result + return to origin

Entry: the session flow

Sign-in Sign-in screen→ Validate→ Role resolved→ Landing for that role
  • Wrong credentials — one message above the form: what to do next, not what failed technically. The typed identifier survives; only the password field clears.
  • Forgotten password — no self-service email reset is assumed, because no mail system exists in this project. The screen states who to contact, and the Super Admin resets it from المستخدمون والصلاحيات. See D4.
  • Session expiry — signing back in returns the user to the screen they were on, not to the dashboard. Any unsaved form content is restored with it (R4).
  • Landing by role — Super Admin and Admin land on الرئيسية; a Content Manager lands on the content-shaped variant of it.
05

The context contract

R3 is the rule most easily broken by accident, so it is specified rather than asserted. "Return to the appropriate previous context" means exactly this:

What is preservedRule
List stateActive filters, search text, sort, page and scroll position are all restored on return. They survive a full page reload, because they live in the address, not in memory.
OriginReturn goes back to where the user came from, not to a fixed page. A request opened from a customer profile returns to that profile. The same request opened from the dashboard returns to the dashboard's filtered list.
After saveEditing an existing record returns to the record, updated, with an inline confirmation. The user stays where the work is.
After createCreating lands on the new record, not back on the list — the admin is usually still on the phone and needs to read back what was captured.
After status changeStays on the record. The state on screen updates in place. No navigation.
After delete or hideReturns to the list, with the same filters, and says what was removed.
After cancelAbandoning a form returns to the exact origin and changes nothing. If anything was typed, the user is asked first (R4).

Why the address bar carries filter state

Because it is the only mechanism that survives a reload, a back button, a shared link and a session timeout at once. A dashboard counter reading طلبات جديدة is then simply a link to the requests list already filtered — one mechanism serving navigation, restoration and hand-off to a colleague, instead of three.

08

Requests — discovery

Five entry points, one destination. The list is the module's home and remembers how it was left.

Discovery Entry point→ Requests list→ Search / filter / sort→ Open the request
  • Entry points — primary navigation; a dashboard count (arrives pre-filtered); the dashboard quick action (arrives at the record form); a customer's request history; global search by name, phone or request number.
  • Default view — everything, newest first. New requests are marked in the row itself, so the default view never hides them behind a filter the client has to know to apply.
  • Sort — creation date and trip date, ascending or descending. Two axes, because those are the two the work actually turns on: what came in, and what is coming up.

Requests — the record

Opening a request opens a focused screen, not a modal. The order below is the order the information is needed in during a call, which is not the order it was collected in.

#BlockHoldsWhy it sits here
1Identity & stateRequest number, current status, created dateThe first question is always "where is this one?"
2Customer & contactName, phone — with call and WhatsApp actions attachedThe second thing anyone does is reach the customer. The action sits on the number, not in a menu.
3ServiceOne of the 7 approved servicesDetermines the vehicle and the crew.
4The tripPickup, destination, date and timeRead together, in that order, because that is the sentence being confirmed on the phone.
5NotesFree text, appended over time, each entry stamped with who and whenThis is where everything the form did not anticipate lands — including why a request was cancelled.
6Status historyEach change: from, to, by whom, whenAnswers "who confirmed this?" without a phone call. Read-only.

Actions on a request

  • Primary — تغيير الحالة. One control, always in the same place, moving the request along the lifecycle in §10.
  • Secondary — اتصال, واتساب (both act on the stored number), تعديل الطلب, إضافة ملاحظة.
  • Consequential — إلغاء الطلب. Sits apart, at the end of the action set, never styled as the obvious next step, and always confirmed (§20).
  • Not offered — deleting a request. A cancelled request is a business fact worth keeping; erasing it destroys the customer's history and the report counts along with it (R7).

Recording a request — the F1 flow

On the call تسجيل طلب→ Phone number first→ Known customer? auto-fill→ Trip details→ Save→ The new request, ready to read back
  • The phone number is the first field, because it is what the caller gives first and because it is the key that decides whether this is a returning customer. If it matches, the name and any notes fill in and the screen says so — عميل مسجّل مسبقاً — rather than quietly creating a duplicate.
  • One screen, one save. No wizard, no steps. A caller does not read their details in the order a multi-step form wants them, so every field stays reachable at once.
  • Typed input is never lost — not on a validation failure, not on a connection error, not on an accidental back. This form carries R4 more than any other screen in the product.
  • New requests start at جديد. The status control is not part of the create form.

The status lifecycle

The approved five. No operational statuses are added at this stage.

جديدRecorded, not yet looked at
→
قيد المراجعةBeing checked and arranged
→
مؤكدAgreed with the customer
→
مكتملTrip carried out · final
ملغي Reachable from any state before مكتمل. Final once set. Always confirmed, and the reason is written into the notes rather than becoming a new field.
MovementBehaviour
Forward, one stepThe default and the easiest thing to do. The control names the destination, so the client reads تأكيد الطلب rather than picking from a menu of five.
To مؤكد, مكتمل or ملغيConfirmed before it happens. These are the three the customer feels, and two of them are final.
BackwardAllowed, because mistakes happen and the alternative is a wrong record standing forever. Confirmed, and the correction is visible in the status history.
Out of a final stateNot offered. مكتمل and ملغي close the record. A customer who calls back needs a new request, not a resurrected one.
Skipping a stepAllowed forward — a request phoned in and agreed on the spot goes straight to مؤكد. Forcing a fictional review step teaches the client to lie to their own dashboard.

How the state reads (R6). Every status appears as its Arabic word, in a consistent position on the row and on the record. Its colour and its shape reinforce that word and never replace it: a status is still legible in greyscale, to a screen reader, and to someone who cannot distinguish the two warm tones.

11

Customers

Customer flow العملاء→ Search / filter→ Customer profile→ Their requests, in place
  • The profile is one screen. Information, contact actions, notes and the full request history sit together. Understanding a customer must never cost a second navigation — that is the whole promise of the module.
  • Request history lists trips newest first with service, date and status. Opening one goes to the request; returning comes back to the profile, per §05.
  • Primary action — تسجيل طلب لهذا العميل, with the customer already filled in. This is the returning-caller flow, and it is one tap from their history.
  • Secondary — اتصال, واتساب, تعديل البيانات, إضافة ملاحظة.
  • Records are created by the work. Recording a request for an unrecognised number creates the customer automatically. Manual creation exists too, but it is the secondary path — a customer with no request is rare.
  • The phone number is the identity. It is what the caller offers and what the admin searches. Matching on it at record time is what stops the same customer existing three times.
  • Deletion is not offered — a customer carries request history, and removing them would silently rewrite it. See D5.
12

Services

Service flow الخدمات→ The 7 services→ Service→ تعديل→ حفظ → back to the list
  • The list is the approved set, shown in the order the website publishes them, each identified by its own name. Seven items — no pagination, no search, nothing to hunt for.
  • Editing covers the service's own published wording. Nothing technical is exposed.
  • Show / hide is the reversible control: a hidden service disappears from the website and stays in the dashboard, clearly marked. This is how a service is retired without destroying it.
  • Ordering changes the sequence on the website. Drag on desktop; explicit up and down controls on touch, because dragging inside a scrolling page is a poor bargain on a phone. Both paths produce the same result and save on the same action.
  • No adding, no deleting. The seven are approved. Adding an eighth is a business decision, not a dashboard action — and the site's own layout and imagery are built for the approved set.
  • States — no empty state exists here, by definition. Loading, saving, error, and the unsaved-changes guard all behave exactly as §19 specifies.

Two editor shapes, and only two

  • Single entry — the area opens straight into its editor. There is one of it; a list of one is a wasted screen.
  • Repeating list — the area opens a list of its items, in published order, with add, edit, reorder and show/hide. Item editing follows §19 exactly.
  • Every editor states where the words land — the section name, as the visitor sees it.   • Nothing technical is exposed — no identifiers, no markup, no layout fields (R10).

FAQs & testimonials

Same list-and-editor mechanics, one deliberate difference in the control that governs visibility — because the two content types differ in who wrote them.

FAQ الأسئلة الشائعة→ List→ إضافة / تعديل→ حفظ→ مفعّل / غير مفعّل
Testimonials آراء العملاء→ List→ إضافة / تعديل→ اعتماد / إخفاء→ حفظ
  • The FAQ toggle is about readiness — the company wrote the answer, and it is either ready to show or not. A half-written answer stays غير مفعّل.
  • The testimonial control is about approval — the words came from a customer, and publishing them is a decision. A new testimonial is never visible by default; it waits for اعتماد. That default is the entire reason the two controls are not identical.
  • Ordering works in both, using the same control as services (§12).
  • Both carry the F2 status — لا تظهر على الموقع بعد — stated on the list and in the editor, so the client is never left believing they have published something the visitor can see.
  • Removal is hiding, not deleting, in both. Deleting is offered only for an item never approved.

16

Users & permissions

Users flow المستخدمون والصلاحيات→ User list→ User→ Role & access→ حفظ
  • The role is chosen as a sentence, not a matrix. Each role is described by what the person can do — "manages the website's content and services" — with the module list shown underneath as confirmation. The client picks a role; they do not assemble one.
  • Admin is the only role with adjustable access, and it is adjusted by ticking the modules from Stage 01's operational set. Super Admin and Content Manager are fixed, because a role that can be edited into anything is not a role.
  • Actions — إضافة مستخدم, تغيير الدور, تعطيل المستخدم, إعادة تعيين كلمة المرور.
  • Disable, don't delete. A disabled user cannot sign in, and everything they did stays attributed in the request history. Deleting them would blank out the record of who confirmed which trip (R7).
  • Two guards, stated in the interface before they are needed — a user cannot change or remove their own role, and the last Super Admin cannot be disabled or demoted. The control is unavailable with the reason shown, not a failure after the fact.
  • Access is enforced everywhere, not just in navigation: a link, a bookmark or a returning session that points into a forbidden module is met with an explanation and a way back, never a blank screen.
17

Reports

Reports flow التقارير→ Report + period→ Results→ Drill into the matching requests
  • Four reports, no more — requests by status, requests by service, requests over a period, and new customers. Each is a count the client can act on.
  • One period control, using the same options and the same words as the requests filter (§18). Learning it once is the point.
  • Every figure is a link into the requests list filtered to exactly the rows behind it. A number the client cannot open is a number they cannot trust.
  • Read at a glance. Each report opens with the answer in words, then the breakdown. No dense analytics surface at this stage.
  • Empty period — says there were no requests in that period and offers a wider one, rather than showing a row of zeroes.

Forms

20

Destructive actions

Destructive Action→ Confirmation naming the record→ Result, stated
  • The confirmation names the thing. Not "are you sure?" but the record and the consequence: this request, this customer, and what will happen to it.
  • The buttons say what they do. إلغاء الطلب and تراجع — never a bare yes and no, which force the client to re-read the question to know which is which.
  • Never the primary action. A destructive control is never the most prominent thing on a screen and never sits where the safe primary action sits elsewhere. Nothing destructive is reachable by muscle memory.
  • Reversible first (R7). Where hiding does the job, deletion is not offered at all — that is why services, customers, requests, testimonials and users are hidden, cancelled or disabled rather than deleted.
  • Status changes get confirmation, not warning. Confirming or completing a trip is consequential but ordinary. It is confirmed calmly, and it is undone by another status change (§10), not by an undo affordance that promises more than it can deliver.
  • The result is stated. Every destructive action reports what happened, in the same words the confirmation used.

The four states

Defined once as behaviour, then applied module by module in §25.

StateBehaviour
Empty · nothing yetExplains what would appear here and how it gets here, then offers the action that creates the first one. The requests list explains that requests are recorded from calls, and offers تسجيل طلب.
Empty · nothing matchedA different state, and it must not be confused with the one above. It says nothing matched the current filters and offers إعادة تعيين. It never suggests creating a record.
Loading · firstPlaceholders that hold the shape and size of what is coming, so nothing shifts under the cursor when content lands.
Loading · subsequentFiltering or sorting an already-loaded list keeps the list on screen and marks it as updating. The screen never goes blank on a change the client just made.
ErrorSays what failed, in the client's terms, and offers the recovery — retry, or go back. Never a code. Never a dead end. A failure in one part of a screen does not take down the parts that work.
SuccessConfirmed in words, near the work, and it disappears on its own. It does not block, it does not move focus, and it does not require dismissal — except after a destructive action, where it stays until acknowledged.
PermissionReaching something out of role explains that the area is not part of their access and offers the way back — never a blank screen or a raw error.

The table-to-card rule

When a table becomes cards, columns are dropped by priority, never squeezed. A request card keeps the customer name, the service, the trip date and the status — the four facts that let the admin decide whether to open it. The request number and creation date live in the record. Nothing is truncated to fit; anything that does not fit is not shown on the card.

Accessibility

Behavioural requirements only. Contrast values, sizes and focus styling are set in Stage 03 against these rules.

  • Arabic hierarchy is real — heading, label, body and caption are distinguishable without reading them, in a face that renders Arabic properly at every level.
  • Contrast is sufficient for body text, labels, status words and the disabled state alike. The disabled state is the one usually forgotten, and it still has to be readable.
  • Targets are large enough and separated enough that adjacent actions — particularly a safe action next to a consequential one — cannot be confused by a thumb.
  • Everything is reachable by keyboard, in the reading order, right to left. Filters, sheets and confirmations trap focus while open and return it to the control that opened them.
  • Focus is always visible, on every interactive element, including inside overlays.
  • Labels are permanent and meaningful. Icon-only controls carry a name for assistive technology.
  • Status is text first (R6) — colour reinforces the word, never replaces it, so status survives greyscale, colour blindness and a screen reader.
  • Errors are tied to their field and announced, so someone not looking at that part of the screen still learns what went wrong.
  • Save results are announced without stealing focus, so a keyboard or screen-reader user knows the save landed and keeps their place.
  • Structure is meaningful — landmarks, real headings and real tables, so the page can be navigated by structure rather than by scrolling.
  • Language and direction are declared as Arabic, right to left, matching the site.

Open decisions

Six points where the build needs a client answer. Each has a working assumption, so Stage 03 is not blocked on any of them.

#QuestionWorking assumption
D1Is a request form being added to the website, or do requests stay phone and WhatsApp only?Phone and WhatsApp only. مصدر الطلب is recorded so a website source can be added later without restructuring the module.
D2Are الأسئلة الشائعة and آراء العملاء getting sections on the website?Not yet. Both are manageable and clearly marked as not appearing on the site (F2).
D3Can content preview show unsaved edits in place, or only the published version?Published version, opened in its place on the site and labelled as such. A true draft preview is an upgrade, not a requirement.
D4How is a forgotten password recovered, with no mail system in the project?The Super Admin resets it from المستخدمون والصلاحيات, and the sign-in screen says so.
D5Does the client ever need to delete a customer outright?No. Deletion would silently rewrite request history and report counts.
D6The site says شركة عون الدرب للنقل المتخصص; the brief says وكالة. Which is the registered name?The site, as the source of truth. The value is editable in معلومات الشركة, so correcting it is a settings change, not a rebuild.

Held back for later, deliberately

Drivers, vehicles, scheduling, dispatch, notifications, payments and advanced reporting are not modules and not screens in this stage. The architecture accommodates them — each would enter as a new primary module beside the eight, reusing P01–P10 without changing them — but none is built, exposed or hinted at in the navigation.

Handoff to Stage 03

  1. Ten patterns need visual form — P01 to P10 in §24. Designing these ten designs the whole product; designing screens one by one does not.
  2. Five statuses need a visual treatment that survives greyscale (R6) — a word, a shape and a position, with colour reinforcing rather than carrying the meaning.
  3. Three list densities — the desktop table, the tablet reduction, and the mobile record card, with the drop-by-priority rule from §22 applied to requests, customers and users.
  4. The record form is the screen to design first. Because of F1 it is used under time pressure, on a phone, mid-call. If it works there, everything else in the product is easier.
  5. Arabic typography carries the hierarchy — heading, label, body, caption, and the status word, all in a face that holds up at small sizes in an RTL table.
  6. Four state treatments — the two empties, loading, error and success from §21, as a set, so they are recognisably related.
  7. Not yet decided, and out of scope until Stage 03 — colour, type scale, spacing, radius, elevation, motion, iconography and component anatomy. None of it is implied by anything above.
