02

Why PHP, not Node

HOSTINGER.md documents the actual deployment: a zip extracted into public_html on Hostinger shared hosting, served by LiteSpeed. That environment runs PHP and MySQL natively. It does not run Node.

§33, in the brief's own words

Do not introduce infrastructure that cannot realistically run in the existing hosting environment. A Node backend would have meant a Hostinger VPS or their separate Node.js product — a different plan, a different deployment procedure, and a process manager to keep alive. That is a real option, but it is a change of hosting, not a backend recovery, and it would have made the deployment document wrong.

So the API ships inside the same zip, and the upload procedure is unchanged: the operator extracts one archive and runs two commands. Everything the backend needs — PDO, Argon2id, MySQL — is already on the plan.

04

The request path

Every /api/* URL arrives at one front controller. The gates run before the handler, driven by the route table, so a handler cannot forget a check it never had to remember.

Protected admin call browser→ api/index.php→ CSRF→ Auth→ Authz→ handler→ Repo→ MySQL
Public submission form→ rate limit→ CSRF→ honeypot→ validate→ fingerprint→ transaction→ REQ-YYYY-NNNN

The application itself lives in app/, which is denied to the web twice over: its own .htaccess, and a guard constant in every file so a host that ignored the first would still return nothing rather than source.

05

Guards only a server can hold

§10 is the heart of this stage: authentication alone is not enough, and a hidden button is not a permission. Two rules in particular were one HTTP request away from being broken, whatever the interface showed.

Self-escalation

An operator cannot raise their own role

The users module already refused to draw the control. That refusal lives in the browser, and the browser is the attacker's. The server now returns 409 and changes nothing — verified by making the call directly and re-reading the row.

Lockout

The last active Super Admin cannot be removed

Demoting or disabling the only remaining Super Admin would leave the system with nobody who can manage accounts. Counted server-side, on every save, against the live table rather than the page's copy of it.

A third holds the session itself: disabling an account revokes its live sessions, so an operator who is switched off is signed out rather than remaining signed in until their cookie happens to expire.

06

POST /api/requests

The endpoint the public form has been posting to since the day the form was added. It accepts exactly the fields the approved form has and nothing else — a submission carrying an extra key is rejected as a malformed payload rather than trimmed, because the alternative is guessing which caller sent it.

  • Status is جديد, always. There is no parameter that lets a public caller pick a status, a source or a customer. §15 asks for it; the absence of the parameter is what enforces it.
  • One transaction. Customer, request, opening history row, reference number, fingerprint and notification, all or none. The states §18 names as unacceptable — a customer with no request, a request with no customer — cannot occur.
  • The reference is allocated under a row lock. Two simultaneous submissions cannot take the same number, and the four-digit tail widens rather than truncating past 9999 — the defect Stage 16 found in the demo id builder, fixed at the source.
  • Duplicates are answered, not merged. A fingerprint of what makes a trip that trip catches a double click, a browser retry or a refresh inside a ten-minute window and returns the id it already has. Change the destination and it is a different trip with its own record — §19 is explicit that genuinely separate requests must not be merged.
  • The honeypot answers with a success. A bot that filled the invisible field gets a plausible reply and no database row, so it does not learn to avoid the field.

Zero console errors, zero horizontal overflow.

08

Deployment

Unchanged from before: one zip, extracted into public_html. Two commands and one file are new.

  1. Create a MySQL database in hPanel and note the three values.
  2. Write .env one level above public_html, from the shipped .env.example. Above the web root is the point: nothing there is reachable over HTTP under any misconfiguration. Inside app/ also works and is denied by .htaccess, but it is the weaker of the two.
  3. php bin/migrate.php — creates the tables, safe to re-run.
  4. php bin/seed.php --admin-email=… — loads the seven approved services and the media index, and prints a generated password once. It is never written to the log or the database; only its hash is stored.
  5. Open /api/health. It reports which settings are present, never their values, so it is safe to open in a browser.

The failure mode that matters

If admin/.htaccess does not upload — it is a dotfile, and file managers hide those — the admin pages are served as plain static files and are readable by anyone with the URL. HOSTINGER.md lists this with the instruction to take the site down until it is fixed, because it is the one deployment mistake that silently undoes this entire stage.

09

What this still is not

Recorded here rather than left for the next audit to find.

  • Three modules still render seeded data in the browser. الخدمات، الوسائط والأصول and الإعدادات have protected read and write endpoints, and those endpoints work — the pages have not been switched over to them. طلبات النقل، العملاء، المستخدمون والصلاحيات، سجل النشاط and the notifications are live.
  • المحتوى and التقارير remain unbuilt. Their permissions exist in the matrix; the modules do not.
  • No email, no SMS. The settings page has always said so, and it is still true.
  • Rate limiting is per IP address. Behind a shared NAT — an office, a mobile carrier — that is a shared budget, and a legitimate second visitor can be throttled by the first.
  • Roles gate modules, not rows. An operator who can see طلبات النقل can see every request in it. That matches the approved design; it is worth knowing it is the design.
  • Verified against SQLite locally, targeted at MySQL. The SQL is kept to the portable subset both accept and the per-driver differences are isolated, but the 108 checks ran against SQLite. The first run of migrate.php on the real host is the confirmation, and /api/health is how you read it.

Sensible next steps

  1. Deploy and run the two commands, then open /api/health and submit one real request through the public form.
  2. Switch the three remaining modules to their endpoints — the work is per page and the APIs are already protected and tested.
  3. Re-run the QA gate against the deployed system. The Stage 16 verdict was NOT READY on six blockers; five of them are now addressed, and the sixth — verifiable Hostinger deployment — can only be closed on the host itself.
